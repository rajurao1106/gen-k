# Gen-K

Gen-K is a Next.js App Router application with server-rendered SEO landing
content and an interactive astrology experience. It includes online kundali,
kundali milan, numerology, mahadasha and AI Friend tools.

## Requirements and local development

- Node.js 20.9 or newer
- npm

Install dependencies and run the frontend and Express API together:

```powershell
npm install
Copy-Item .env.example .env
npm run dev
```

Next.js runs at `http://localhost:3000`; the Express API runs at
`http://localhost:5000`. Before starting, set `MONGODB_URI`, `JWT_SECRET`,
and `DEMO_PAYMENT_SECRET` in `.env` (configured secrets must contain at least
32 characters). Local development has a fallback `JWT_SECRET`; production
requires it to be configured explicitly. Use a
dedicated local/test MongoDB replica set because account, payment, and referral
flows use transactions. `npm run build` creates a production Next.js build,
and `npm start` serves that build. At startup, the API removes a legacy unique
`username` or `email` index from the users collection when present; the current
phone-based account model does not use either field.

## Deploy to Vercel

Import this repository into Vercel and use these project settings:

- **Root Directory:** repository root (`./`, where `package.json` lives)
- **Framework Preset:** Next.js
- **Install Command:** `npm ci`
- **Build Command:** `npm run build`
- **Output Directory:** leave the default / empty

The root `vercel.json` declares the framework, install command, production
build command and API rewrite. Do not use `npm run dev` as the Vercel Build
Command: it starts the local Next.js development server and Express watcher,
which keep running instead of producing a deployment build. The Express API is
served on Vercel through `api/index.js`; keep the `api/` and `server/` folders
in the project.

After importing, configure the environment variables listed below in Vercel
for **Production**, **Preview** and/or **Development**, as needed. Push changes
to the connected Git branch to trigger a deployment. If an older deployment
is stuck in `Building`, cancel that deployment in Vercel and inspect the new
deployment's Build Logs; it should run `npm run build`, not `npm run dev`.

## Environment variables

Configure server-only API keys and database credentials in the Vercel project
environment; do not add them to source control. Gemini accepts
`GEMINI_API_KEYS` or the numbered `GEMINI_API_KEY` variables. AI features use
`gemini-3.5-flash-lite` by default. If `GEMINI_ALLOWED_MODELS` is set, include
`gemini-3.5-flash-lite` in its comma-separated values.

Account creation requires `MONGODB_URI`. Production also requires `JWT_SECRET`
(at least 32 characters). Phone numbers are not verified: a new number creates
an account immediately, while an already-registered number cannot sign in.
Same-origin browser/API requests are accepted automatically.
If the frontend and API use different origins, set `CORS_ORIGINS` to the
comma-separated exact frontend origins (scheme and host, no path), for example
`https://app.example.com`.
Configure `ADMIN_PHONES` as a comma-separated list of E.164 numbers allowed
to use administrator login. Set `ADMIN_LOGIN_PASSWORD` to a unique,
server-only password of at least 32 characters for `/login`. Admin numbers are
blocked from public signup. Do not expose the password through a `NEXT_PUBLIC_`
or `VITE_` variable.
`REFERRAL_PHONE_HMAC_SECRET` is optional. When migrating from the previous OTP
setup, set it to the old `OTP_SECRET` value to preserve existing referral
phone-hash checks; after migration, the legacy `OTP_SECRET` variable is no
longer used.

`PAYMENT_MODE=demo` and `DEMO_PAYMENT_SECRET` enable simulated checkout; it
creates no real charge and is disabled in production by default.
`PAYMENT_MODE=razorpay` enables Razorpay payments. By default, only server-side
test credentials (`RAZORPAY_KEY_ID=rzp_test_...` and `RAZORPAY_KEY_SECRET`)
are accepted. Use Razorpay Dashboard test credentials and test payment methods;
configure automatic payment capture so successful test payments can be verified.

For an actual ₹1 payment test only, set `MONEY_TESTING=true` and configure
separate server-only live credentials (`RAZORPAY_LIVE_KEY_ID=rzp_live_...` and
`RAZORPAY_LIVE_KEY_SECRET`). Keep `RAZORPAY_KEY_ID=rzp_test_...` and
`RAZORPAY_KEY_SECRET` as the test credentials. This exposes a ₹1 plan with the
same unlimited Kundali chat and AI Friend access as the ₹19 plan. Live
credentials are used only for the ₹1 plan; other plans continue to use test
credentials. Anyone who can access the live site can see and buy this plan
while the flag is enabled, and each purchase charges real money. Canceling
revokes access and does not refund the payment. Turn `MONEY_TESTING` off after
testing and redeploy. Never expose either key with a `NEXT_PUBLIC_` prefix,
commit secrets, or paste them into chat.

The regular ₹19 one-time plan grants unlimited Kundali chat and AI Friend
replies after the 10 free replies; voice cloning remains a separate add-on.
`GEMINI_API_KEYS` accepts a comma-separated list of server-only keys, or use
`GEMINI_API_KEY`, `GEMINI_API_KEY_2`, etc. `BOSON_API_KEY` is required for
Boson AI Higgs TTS voice generation and must remain server-only. The voice
provider base URL and preset voice can be configured with
`VOICE_PROVIDER_BASE_URL` and `VOICE_PRESET`. Remaining rate-limit, provider,
and site settings are documented inline in `.env.example`; never commit `.env`
or paste credentials into source files.

### Account smoke test

Use a dedicated local/test MongoDB database. Configure `JWT_SECRET`,
`ADMIN_PHONES`, and `ADMIN_LOGIN_PASSWORD`, then start `npm run dev`. Submit a
new mobile number at `/account`; verify an account is created immediately,
`/api/auth/me` returns it, and onboarding opens. Submit the same number again
and verify signup is rejected. Save a profile and verify it is associated with
the new account. Log out and confirm protected data requires a session. Verify
that a regular account cannot access `/api/users/all` (403) and an
unauthenticated request to `/api/users/me/profiles` returns 401. Verify admin
login works only with a configured admin number and the server-side password.

Existing records without an owner are deliberately not assigned to a newly
authenticated user. To mark them as legacy/unowned before rollout, run
`node server/scripts/migrateUserDetails.js` against the intended database.

### Phase 2: plans, entitlements, usage, and daily guides

`GET /api/plans` exposes the read-only plan catalogue. Prices are display
amounts in paise. Authenticated
`GET /api/me/entitlements` returns the current plan, active entitlements, and
today's usage summary. `POST /api/guide/today` accepts `{ "profileId": "..." }`,
checks that the profile belongs to the signed-in user, then returns or generates
the guide for that profile and the current Asia/Kolkata day. A unique database
index and generation lease prevent duplicate daily guide records and concurrent
Gemini generation for the same user/profile/day.

Manual verification (use a dedicated development MongoDB database with a
Gemini key configured):

1. `GET /api/plans` returns Free and the ₹19 unlimited AI chat plan.
2. Without a session, `GET /api/me/entitlements` and `POST /api/guide/today`
   return 401. With a session, the entitlements response starts at the Free
   plan with ten lifetime AI replies available.
3. Save two profiles under one account and one under another. Request today's
   guide for each owned profile; repeat the request and confirm `cached: true`
   and that one `DailyGuide` exists per profile/day.
4. Request a profile ID belonging to the other account and confirm the API
   returns 404 without generating or disclosing its guide.
5. Call `incrementUsage` concurrently beyond a test limit and confirm no more
   than that limit of calls are allowed for the Asia/Kolkata day key.

### Phase 3: demo and Razorpay test payments

Set `PAYMENT_MODE=demo` and configure `DEMO_PAYMENT_SECRET` with at least 32
characters. Demo checkout generates server-signed fake payment proofs and never
contacts a payment gateway or moves money. Demo payment routes are disabled in
production unless `ENABLE_PRODUCTION_DEMO_PAYMENTS=true`; when enabled, any
signed-in user can activate plans without paying.

Authenticated endpoints:

- `POST /api/payments/create-order` with `{ "planId": "ai_chat_unlimited" }`
  reads the amount only from the server-side plan catalogue.
- `POST /api/payments/demo/complete` with `{ "orderId": "...", "outcome":
  "success" }` simulates a successful payment for legacy demo orders; it cannot
  activate the current ₹19 unlimited plan.
- `POST /api/payments/verify` accepts the `orderId`, `providerPaymentId`, and
  `signature` returned by the success simulation. Replaying verification is
  idempotent.
- `POST /api/payments/demo/refund` with `{ "orderId": "..." }` refunds a paid
  demo order and revokes its entitlement.
- `GET /api/payments/history` returns the signed-in user's recent orders.

For local simulation, use `PAYMENT_MODE=demo`. To test Razorpay, set
`PAYMENT_MODE=razorpay` and provide test credentials in the server environment.
Checkout creates the order using the server-side plan price. The server verifies
the Razorpay HMAC signature and confirms the payment is captured and matches the
order amount, currency, and provider order ID before granting access. Verify a
successful ₹19 payment grants one permanent entitlement and that retries do not
grant it twice. Test cancelled and failed checkouts and confirm they grant no
access. MongoDB transactions commit order state and entitlement changes
atomically, so the database must support transactions (for example, a replica
set or MongoDB Atlas). Live keys and live charging are intentionally not
supported yet; production refunds and webhook-based reconciliation must be
implemented before enabling real payments.

   ### Phase 4: server-side feature gates and quotas

   `POST /api/gemini` now requires a purpose (`chat`, `kundali`, `milan`,
   `mahadasha`, or `guide`) and is protected by both IP and per-user request
   limits. Free accounts get 10 lifetime AI chat replies across Kundali chat and
   AI Friend; the ₹19 one-time entitlement removes that quota. Premium accounts
   retain their configured daily quota.
   Mahadasha and full daily-guide content require premium; free users still receive
   the daily-guide preview. The full Kundali and Milan report calls include a
   server-validated report identity, consume an eligible report credit once, and
   are persisted per account so retrying the same report returns the saved result
   without consuming another credit. Failed generation restores the consumed
   credit.

   `POST /api/voice/speak` requires the voice add-on, is rate-limited per user, and
   counts generated text characters against `VOICE_CHARACTERS_PER_DAY` (Asia/
   Kolkata day). Characters are refunded when the upstream speech request fails.
   Voice sample deletion is rate-limited per user. Speech synthesis uses a
   three-request provider concurrency limit; request and deletion settings are
   listed in `.env.example`.

   Manual verification (use a dedicated development MongoDB database):

   1. Confirm unauthenticated Gemini and voice requests return 401. Authenticated
      Gemini requests without a valid purpose return 400.
   2. On a Free account, send ten chat requests across Kundali chat and AI
      Friend; confirm the eleventh returns `402 QUOTA_EXCEEDED`. Verify the
      lifetime count is shared across both features and survives a new day.
      After a verified ₹19 payment, confirm both features are unlimited.
   3. Confirm Mahadasha and full-guide requests return `402 UPGRADE_REQUIRED`
      for Free. Free `/api/guide/today` responses contain the preview only
      (belief, power, caution, lucky number, and color), with no remedy or full
      guide fields.
   4. Grant a test Milan or Kundali report entitlement, generate the same report
      twice, and confirm the second request returns the persisted report without
      decrementing `remainingUses` again. Force a Gemini failure and confirm the
      report credit is restored.
   5. Grant the voice add-on, submit text through `/api/voice/speak`, and verify
      successful characters increment the daily counter. Set a low test limit and
      confirm exceeding it returns `402 QUOTA_EXCEEDED`; verify a failed upstream
      request refunds its character count.

   ### Phase 5: plans and paywall UI

   The authenticated `/plans` screen displays the server plan catalogue, current
   plan, remaining AI replies, and recent payment orders. Only the ₹19 unlimited
   AI chat plan is available to purchase; older plans are not listed or accepted
   for new orders. Existing entitlements are preserved. Checkout uses Razorpay
   test mode; demo checkout cannot activate the unlimited plan.

   Manual verification (use a dedicated development MongoDB database and
   Razorpay test credentials):

   1. Open `/plans` and confirm only Free and the ₹19 unlimited plan are
      available, along with current access, usage, and order
      history load for the signed-in account.
   2. Exhaust the 10 free replies and follow the AI Friend or Kundali link;
      confirm the ₹19 plan is highlighted.
   3. Complete a Razorpay test checkout and confirm the ₹19 entitlement and
      recent order update; confirm a failed/cancelled checkout grants nothing
      and no real money is charged.
   4. Confirm old entitlements remain intact while old plans are not offered
      for new purchases.

   ### Phase 6: voice consent and ownership

   Voice cloning uses Boson AI Higgs TTS 3 reference audio. Cloning requires the
   account's active voice add-on and an explicit consent confirmation; the server
   records the confirmation version and whether the sample is the user's own or
   was shared with permission. Reference audio is stored with each account-owned
   voice profile and sent to Boson AI only when speech is requested. Profiles can
   be listed, spoken with, or deleted only by their owner. Reference audio and
   provider credentials are never returned to the browser. Voice replies are
   AI-generated.

   Manual verification (use a dedicated development MongoDB database, a Boson
   API key, and a demo voice add-on):

   1. Without the add-on, confirm cloning and speaking return
      `402 UPGRADE_REQUIRED`.
   2. With the add-on, submit an upload without the consent header and confirm
      the server rejects it. Confirm the upload button remains disabled until
      both the consent statement and voice ownership/permission choice are set.
   3. Save multiple voices under one account. Sign into another account and
      confirm it cannot speak with or delete those voice profiles.
   4. Sign into the original account from another browser and confirm its voice
      profiles load. Delete a voice and confirm its reference audio and database
      record are removed.

   Frontend settings use the `NEXT_PUBLIC_` prefix:

- `NEXT_PUBLIC_SITE_URL`: canonical production origin; recommended for SEO.
- `NEXT_PUBLIC_API_URL`: optional API origin. Leave unset on Vercel to use the
  same-origin `/api` serverless function. Local development defaults to port
  `5000`.
When migrating an existing `.env`, rename any `VITE_API_URL` setting to
`NEXT_PUBLIC_API_URL`.
Remove any `VITE_ADMIN_PASSWORD` or `NEXT_PUBLIC_ADMIN_PASSWORD` setting.
`ADMIN_LOGIN_PASSWORD` must be configured only in the server environment;
successful login creates or promotes an admin account for a number in
`ADMIN_PHONES`. Keep Gemini keys server-only.

## AI Friend voice replies

AI Friend chat uses the configured Gemini API key. Voice profiles and reference
audio are stored against the signed-in account; audio and provider credentials
remain server-side and browser state contains no voice identifiers. Cloning and
speech use Boson AI Higgs TTS 3 (`higgs-tts-3`) through the OpenAI-compatible
`/audio/speech` endpoint. Reference audio is sent with each clone request, so
there is no provider-side voice creation step. Every saved sample requires a
stored consent confirmation. If a cloned voice request fails, the server retries
rate-limited requests with backoff and then tries the configured preset voice.
Speech requests use a bounded in-memory concurrency queue and cache generated
audio by text and voice ID.
Browser microphone transcription uses the browser's Speech Recognition API;
the browser may use its own online speech service.

## Phase 7: privacy, SEO, sharing and development tools

The public legal pages are `/privacy`, `/terms`, `/refund`, `/disclaimer` and
`/contact`; update their `[BUSINESS NAME]`, `[EMAIL]` and `[ADDRESS]`
placeholders with reviewed business details before launch. Landing and plans
pages link to these pages. The sitemap includes legal pages and the four
indexable astrology pages.

Signed-in users can delete their account from `/profile`. Deletion removes
owned profiles, guides, reports, voices, entitlements and usage, clears the
session, and anonymizes payment orders. Referral reward records keep only a
keyed phone hash to prevent the same phone from claiming another reward; user
references are anonymized. Saved voice reference audio is deleted with the
account's voice profiles.

Development tools are available at `/dev-tools` only to admin accounts and
only outside production. Public signup cannot create or promote admin accounts;
the separate admin login requires both an allowlisted phone and the server-only
password. Use a non-production database when granting/revoking test
entitlements, resetting usage, expiring subscriptions or viewing orders.

The share card at `/api/og` contains only a whitelisted rashi and fixed insight;
it does not include profile name or birth details. Referral codes award one
Kundali report credit to each account after the referred user completes
onboarding; invalid, self-referrals, and repeat rewards are rejected.

Phase 7 manual verification (use a dedicated development MongoDB replica set):

1. Open each legal link from the landing and plans pages, then check the
   corresponding page title and sitemap entry.
2. Use a test account to complete onboarding with a second account's referral
   code. Confirm each account receives exactly one report credit; try an
   invalid code, the user's own code, and a repeat code/phone and confirm the
   API reports an explicit error without granting extra credits.
3. Share a dashboard rashi card. Inspect the image and WhatsApp URL and confirm
   they contain no personal birth data.
4. As a non-admin, confirm the dev-tools page/API are denied. As an admin in a
   non-production environment, test grant/revoke, usage reset, subscription
   expiry and order listing. Confirm the page returns 404 and `/api/dev/*`
   returns 404 in production.
5. Delete a test account with and without saved voice profiles. Verify voice
   reference-audio deletion, profile/report/guide/entitlement deletion, order
   anonymization, referral-reference anonymization and session clearing.
6. In development, verify `signup`, `kundali_created`, `paywall_viewed`,
   `checkout_started` and `payment_success` are logged without phone, name,
   birth date, time or birthplace. Analytics is console-only in development
   and a no-op in production; no third-party analytics provider is configured.

## Phase 8: local/dev QA and hardening

`GET /api/health` reports only the API status and MongoDB connectivity. It
returns HTTP 200 when the database ping succeeds and HTTP 503 with a generic
unavailable response when MongoDB is disconnected or the ping fails; it does
not expose connection strings or provider errors. Mutating payment and profile
routes have per-user rate limits. The Gemini key-pool status route requires an
admin account, returns no key fragments, and is hidden in production unless
`GEMINI_STATUS_ENABLED=true`.

### Manual QA checklist

Use two separate test accounts and a dedicated, disposable MongoDB replica-set
database. Configure `PAYMENT_MODE=demo`, `ADMIN_PHONES`,
`ADMIN_LOGIN_PASSWORD`, and a Gemini key. Configure `BOSON_API_KEY` and grant
the voice add-on only for voice checks. Do not use real customer data.

1. **Account creation:** Create an account with a new number and verify it is
   signed in immediately. Retry with that number and confirm the API rejects
   duplicate signup rather than opening the existing account. Confirm numbers
   in `ADMIN_PHONES` are blocked from public signup and admin login requires the
   server-side password.
2. **Ownership:** Create a profile as account A. Create account B with another
   number and try
   to read, update, delete, or request a guide/report for A's profile ID.
   Confirm private routes reject unauthenticated requests with 401 and B cannot
   retrieve or mutate A's data.
3. **Demo payment idempotency:** Create and successfully complete a demo order,
   verify its proof twice, and confirm the second verification is idempotent
   with exactly one entitlement. Try a failed order, replayed/invalid proof,
   refund, and repeat refund; confirm order ownership and status checks hold.
4. **Quotas and paywalls:** Confirm free chat quota returns
   `402 QUOTA_EXCEEDED` at its configured limit, and gated Mahadasha, full guide,
   Kundali/Milan report, and voice operations return `402 UPGRADE_REQUIRED`
   without the relevant entitlement. Confirm the free Kundali basics and guide
   preview remain usable.
5. **Plans UI:** Sign in and load `/plans`; verify plan catalogue, current plan,
   usage and order history. Follow a contextual upgrade link and check the
   recommended plan. Simulate a purchase and verify the UI refreshes without
   contacting a live payment provider.
6. **Voice ownership:** With an add-on and provider key, save multiple voices
   for A. Confirm B cannot list, speak with, or delete them; check missing
   consent, malformed IDs, supported audio formats and size limits. Delete a
   test voice and verify its stored reference audio and database record are
   removed.
7. **Health and admin tools:** With MongoDB available, confirm
   `GET /api/health` returns 200 and `database: "connected"`. Stop/disconnect
   the test database and confirm it returns 503 with no internal details.
   Verify non-admins cannot access `/api/dev/*`; verify admins can exercise
   dev tools outside production and both the page and API are unavailable in
   production.
8. **Build checks:** Run `npm run lint` and `npm run build`. Keep secrets only
   in an ignored local `.env`; never commit it. Use the Razorpay migration
   notes under Phase 3 only as future implementation guidance—real payments
   are not enabled by this development-only phase.

This repository has no automated test runner configured. The checklist above
is the manual verification plan; database/provider-dependent items require the
local services described above and should not be reported as passed until run.
